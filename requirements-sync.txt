# Python dependencies for writing to Supabase.
#
# WHY THIS FILE IS SEPARATE
# -------------------------
# The knowledge engine, the sync framework and the user-intelligence engine
# depend on the standard library alone. That is deliberate: it means the whole
# platform can be reviewed and run on a bare Python.
#
# The test suite no longer can — see requirements-dev.txt, which declares the one
# thing it needs. That file and this one stay separate because they are installed
# at different moments and for different reasons: dev deps BEFORE the tests, this
# one AFTER them, so the suite keeps proving the engine is self-contained in an
# environment where the SDK is genuinely absent.
#
# Exactly one operation breaks that rule — actually writing to Supabase. Both
# writers (`knowledge_sync/adapters.py` SupabaseTarget and
# `user_intelligence/writer.py` SupabaseTarget) import the SDK LAZILY, inside the
# `client` property, so the import cost is paid only by a live sync and never by
# a test, a plan or a dry run.
#
# What was missing was not the import guard. It was this file: nothing declared
# the dependency, and nothing installed it, so the workflow reached the Apply
# step and failed with "the `supabase` package is not installed" — after the
# tests and the plan had both passed.
#
# INSTALL ONLY WHEN YOU INTEND TO WRITE
#
#     python3 -m pip install -r requirements-sync.txt
#
# Do NOT add it to a general requirements.txt. A test suite that quietly gains a
# third-party dependency is a test suite that stops proving the engine is
# self-contained, and `tests/test_user_intelligence.py` asserts that property.

# Pinned to a minor range, not floating.
#
# This writes to production data on every merge to main. An unpinned dependency
# means the bytes that touch the database can change without a commit, and the
# first sign would be a failed sync at 03:00 on a Monday. `~=` allows patch
# releases (security fixes) and blocks 2.32 and 3.x.
#
# Verified against 2.31.0 in a clean virtualenv: every call the adapters make —
# create_client, .schema(), .table(), .upsert(on_conflict=), .update().in_(),
# .select().is_() — resolves. Re-verify when raising this pin.
supabase~=2.31.0

# The direct-Postgres transport, used by `--target postgres` (the default in
# scripts/run_sync.sh).
#
# WHY BOTH ARE HERE
#
# supabase-py talks to PostgREST, which refuses any schema not listed under
# Project Settings -> API -> Exposed schemas — PGRST106, for every caller,
# including one holding the service role key. That is a server configuration and
# no credential routes around it. Nine consecutive CI runs therefore created a
# complete schema and imported nothing into it.
#
# psycopg talks to the database. The sync is an operator process in CI holding
# the database's own DSN; it has no reason to go through the public REST API to
# write a projection, and every reason not to be gated by a setting that governs
# what the public API exposes.
#
# `[binary]` so CI needs no libpq or compiler. Pinned to the 3.x line: this
# writes to production data on every merge to main, and an unpinned driver means
# the bytes reaching the database can change without a commit.
psycopg[binary]~=3.2
